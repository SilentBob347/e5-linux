# E5 网页「无应答」、实体屏幕及上网正常：代码分析

日期：2026-10-24。依据当前 E5 仓库代码与隔离复现，尚无反馈设备的故障现场、固件版本、插件清单及实际配置。用户暂不确定「无应答」位于顶部网络制式还是下方设备状态，因此两条路径均保留。

更新：用户随后要求直接修复已复现的缓存问题。修复已写入共享网页源码并通过浏览器回归，见文末「缓存缺陷修复」。前述分析与复现记录保留为修复前证据。

## 结论

这种组合首先指向网页状态读取路径异常，不能把「无应答」直接解释成基带掉线或 NV 配置损坏。也不能仅凭安装插件在先就认定某个插件有问题。

已确定一个前端缓存合并缺陷；AT 适配设置、独立工程通道失败与状态镜像缺失是需要在反馈设备验证的其他路径。缺陷复现不等于确认反馈设备运行的版本一定含此缺陷，亦不解释第一次 AT 查询为什么失败。

## 两处「无应答」的含义不同

| 位置 | 当前代码的判定 | 可以独立出问题的路径 |
| --- | --- | --- |
| 顶部原 4G/5G 大字 | 合并后的 `c.error` 为真 | 工程 AT 采集、缓存文件、前端合并 |
| 下方设备/基带状态 | `info.modem.alive` 为假 | `/run/e5-mm-state/state.json` 镜像、对应进程存活、启动标识、`/dev/wwan0at0` 存在性 |

入口为 `openwrt/luci-app-t551m/htdocs/luci-static/resources/view/mu300/home.js`；原生状态后端为 `root/usr/share/ucode/e5/dash.uc`。

网页工程数据：`e5status.status` → 后台 `unisoc-modem/cell` → 通用 AT 适配层 → E5 专用适配器 → nr6/nr7 常驻所有者。

屏幕概览：`/api/status` → `modem_status()` 的 ModemManager D-Bus 查询及屏幕缓存；双卡信息另有共享状态来源。它与网页工程采集不是同一套成功/失败判据。网络已有数据连接也不以每轮工程查询成功为条件。屏幕的某些高级详情仍会使用工程查询，不能扩展成「整个屏幕完全不使用 AT」。

## 已复现：成功快档继承了慢档的旧错误

`home.js` 在 `sig.json` 更新且成功时，以 `Object.assign({}, c, {...新字段})` 覆盖旧 `cell.json` 的部分字段，没有去除旧对象的 `error`。随后又通过 `if (c && c.error)` 显示「无应答」。

隔离执行真实 `update()` 中的合并代码，输入慢档 `ts=100,error=...` 和成功快档 `ts=200,cfun=1,reg.stat=1`：

- 成功的完整快档：合并对象时间变为 200，仍带旧 `error`，页面依旧「无应答」。
- 成功的部分首包快档：同样残留旧 `error`。
- 成功的完整慢档替换错误缓存后，才会去掉该错误。

因此它会延长或放大一次采集失败的显示，不能单独断言页面会永久无法恢复。慢档仍在阻塞、反复失败或更新被破坏时，问题会更明显。

复现：在仓库根目录运行 `node work/dashboard-no-response-20261024/reproduce.js`，使用同目录保留的修复前 `home.before.js`。原结果保存为 `reproduction.json`。这是数据合并复现，不是故障设备实测；本节记录分析阶段，后续生产修复见文末。

## 需要现场验证的触发因素

1. **AT 适配设置改变。** E5 默认 `at_backend=custom`、`at_command=/usr/libexec/unisoc-modem/t551m-at`。网页设置允许改成自动、mu300、atinout 或其他自定义路径。改错后工程采集可以失败，而直接使用 ModemManager 的屏幕概览及已连接网络正常。自动检测会受安装的程序影响，例如新增 atinout 后可能选择直接串口访问；不能把「自动」视为等价的 E5 专用模式。
2. **nr6/nr7 工程查询路径异常。** 专用 AT 所有者停止、端点缺失、先前命令超时后仍处于隔离状态，或其他程序直接读取同一串口，都能导致查询失败，nr1 上的拨号路径未必同时失败。正常通过 nr2 专用入口提交命令的插件，并不因此就直接抢占 nr6/nr7；需要进程/文件描述符与服务状态证据。
3. **缓存或后台启动条件受改动影响。** 清理运行目录、目录权限或后台 CPU 策略被其他工具修改，有可能使采集未启动或旧结果不能更新。当前 `e5-background` 对非法 CPU 策略及缺少在线 capacity 信息会报错退出；这属于条件性路径，不能泛指为「省电设置必然导致」。
4. **仅下方设备状态异常。** e5-mm-state 服务停止或镜像文件消失可让网页显示无应答。该值是网页状态镜像判定，不能据此认定 ModemManager 或基带已停止。镜像是事件更新，文件年龄大本身并不证明失效。

采集器还把 AT 客户端 stderr 丢弃，并把多种失败归为 `AT backend did not answer`。因此这个提示不能区分超时、端点不存在、队列过期、通道隔离或适配设置错误。纯 HTTP 请求失败则被页面的 `L.resolveDefault()` 处理，不会直接凭空生成这条顶部 AT 错误，排查重点应先落在返回数据与采集路径。

先保留故障现场，运行：

```sh
python3 diagnose-dashboard.py > /tmp/e5-dashboard-diagnostic.json
```

脚本在本机 `work/dashboard-no-response-20261024/diagnose-dashboard.py`。读取现有快/慢缓存的时间与错误、相关锁的所有者、nr2/nr6/nr7 端点和串口读者、AT 适配设置、后台 CPU 策略及相关服务状态。脚本自身不发送 AT、不调用会触发工程刷新的 status 方法、不重启服务、不修改配置；示例命令的重定向仅用于保存输出。

脚本只摘取必要字段，不导出缓存内的 IMEI、IMSI、ICCID、短信正文或 Wi-Fi 密码。离线私有目录测试已检查缺失文件、故障慢档/成功快档并存、镜像判定和身份字段排除。需要反馈设备的实际输出后，才能把触发原因进一步归到具体配置或程序。

建议后续修正分开处理：先修复已证实的快慢档错误继承，增加采集失败原因与新鲜度的明确展示；再依据现场证据修复适配设置/端口/后台启动问题。不能用持续显示上一次正常信号掩盖当前采集失败，也不应直接回滚无关插件、省电或网络修复。

## 缓存缺陷修复

已修改共享 `view/mu300/home.js`：

- 接受更新或同时间戳的成功快档后清除慢档旧 `error`，复制后合并，避免修改原始 RPC 返回对象。
- 仅在慢档本身正常时保留其工程信号供部分首包使用；从失败状态恢复的部分首包会显示本次成功查询的 CESQ 信息，不再被旧错误或空值挡住。
- 快慢档明确属于不同 SIM 时不合并；慢档重绘标识加入卡槽和当前错误状态，使同时间戳切卡、恢复也能清掉旧详情。
- 保留同卡分阶段采集中已完成的身份、QoS、邻区和工程信号；旧成功数据不覆盖新失败，两档持续失败仍显示「无应答」。

`python openwrt/tests/dashboard-cache-browser.py` 使用真实页面 HTML 与完整 `update()`，在 Chromium 中验证失败→完整快档恢复、失败→部分首包恢复、旧成功数据拒绝、正常部分首包不擦除工程信号、同卡慢档详情保留、同时间戳切卡、不同卡快慢档隔离、持续失败仍报错及输入对象不可变。全部通过。原看板快捷控制确认/取消/失败/离页回归 `node openwrt/tests/dashboard-quick-controls.js` 也通过。

该修复沿用现有共享网页复制与更新路径，六种 profile 均使用此源文件；未修改 AT 后端设置、查询顺序、基带、网络或省电配置。尚未生成新发布包，未在群友故障设备部署，不能把浏览器回归称为该故障设备的实测修复。
