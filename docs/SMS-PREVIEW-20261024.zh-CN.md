# 网页短信摘要检查与刷新修复（2026-10-24）

## 现象与证据边界

用户反馈长分片短信的列表摘要偶尔带 `:0`，正文正常，随后确认目前可能已不可见。
本次只读检查未在当前 T551M 的持久正文、分页摘要接口或新登录的 LuCI 页面中复现。
初次检查的 14 条短信包含多条 2～4 分片长短信，接口摘要均与正文前 100 字相符。
不把“本次看不到”写成已经确认修好了前缀来源。

历史实现曾以固定列宽解析命令行短信列表：21 字符时间列后截取摘要。
若生产者输出完整的 25 字符 ISO 时间戳，时区尾部会落入摘要列，产生类似 `:00` 的前缀。
这是旧接口的风险路径，尚未证明就是本次用户看到的来源。
当前 E5/T551M 的 `t551m-sms` 已直接生成 JSON，时间与摘要独立，不经过这段旧解析。

## 已复现并修复的相关缺陷

当前网页的刷新签名仅包含短信 ID、已读状态及数量。同一 ID 的摘要或正文更新后，
签名不变，网页继续保留旧摘要；正文缓存也只按 ID 保存，无法感知内容变化。
修复前使用真实网页脚本和假 RPC，已复现“更正摘要后仍显示旧摘要”的断言失败。

- 刷新签名覆盖列表显示内容，摘要更正后重绘；完全相同的轮询保留现有 DOM。
- JSON 摘要附加正文 SHA-256 版本，后续分片只改变第 100 字之后的尾部也能使正文缓存失效。
- 正文缓存绑定 ID 与内容版本，忽略旧版本延迟返回的正文，避免覆盖新内容。
- 不删除或改写 `:0` 文本；原文以 `:0` 开头的短信仍正常显示并转义 HTML。

这项修复保证摘要/正文更正后不会因上述缓存规则而残留，不能据此断言已查明历史前缀来源。
