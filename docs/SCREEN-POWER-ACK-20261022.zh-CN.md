# 屏幕电源操作回执修复

## 已确认的代码缺陷

公共 settings API 调用电源操作后，仍执行整页 `settings_items(c)` 读回。
原实现先安排两秒后的正常关机或重启，再查询系统设置、启动选择和更新状态。
若读回异常或尚未结束设备便退出，前端无法获得成功回执，显示失败；操作本身
已经提交。设置页收到成功后还会额外刷新分类，继续访问即将退出的后端。

这是静态代码与模拟时序确认的缺陷；没有通过实际关机复现此次用户报告的
具体异常栈，也没有把所有网络请求失败都当成关机成功。

## 公共修复

- 重启、关机和切 Android 返回明确的 `power_action` 接受回执，API 不再读回
  系统设置。接受只表示命令已安排，不代表硬件已完成关机。
- 检查命令存在和后台提交状态；切 Android 仍先检查原有启动选择操作成功，
  失败时不安排重启。错误回执不再追加设置读取而覆盖原错误。
- 保留原有两秒延迟和正常 `reboot` / `poweroff`，关闭后台任务标准输入输出；
  未使用强制关机，不改变 NV 清理、服务停止、文件系统卸载或启动槽位策略。
- 设置页接受回执后保留操作保护、显示正在执行，不再显示“已保存”或刷新分类。
  电源菜单沿用同一成功回执与禁用重复操作逻辑。
- 通过公共 infoscreen 源码进入全部屏幕机型的构建路径，没有新增机型分叉。

## 验证

- 使用现有 OpenWrt 基础环境的 ucode 执行 `test_screen_power.uc`，模拟后端读回
  已不可用：三种电源操作均能先返回接受；命令缺失、后台提交失败、Android
  选择失败和非法动作仍返回错误。测试未执行任何真实电源或切槽命令。
- Chromium 执行 `test_power_menu_browser.py`：中英文三种设置页电源动作、
  二次确认、防重复和无额外分类读取通过；原电源菜单实体键、锁屏触控开关、
  iframe 焦点、失败后重试及小屏滚动用例通过，无 JavaScript 异常。
- 未热部署或打包，尚未进行实机电源循环验证。
