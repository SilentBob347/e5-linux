# T551M 更新内存检查失败：暂存与 NV 保留修复

## 已确认的原因

用户在安装器“更新 OpenWrt”中收到 `not enough memory for offline update; request not armed`。
NV 电脑备份及上传文件的校验均已通过，尚未启用离线更新，不是 NV 校验失败。

T551M 只读检查：`MemTotal=1532172 KiB`，失败后清除上传目录时
`MemAvailable=1011256 KiB`；待更新载荷约 224 MiB。
原流程把镜像、boot 和约 327 MiB 未压缩工作 NV 归档全部放进 `/tmp`，
再把被这些上传文件及运行服务占用后的 MemAvailable 与离线预算比较，导致误拒绝。
早期离线流程也把已在 RAM 中的 NV 再与剩余内存比较，重复计入占用。

## 修复

- 正常运行的上传／NV 暂存使用根文件系统的 `/.e5-upload-<32位随机标识>`，
  检查根分区可用空间，正常结束／异常退出清理本次目录；不使用 Android userdata。
- 原机恢复候选及旧目录／镜像更新中的 NV 临时文件也放在持久根的 `/opt` 下，
  避开 `/opt/e5/nv` 与 `/etc/e5-nv`，防止归档把自己收进去。
- 内置分区／TF 的电脑备份和早期离线归档使用 gzip 无损传输，完整内容和 SHA256 不变。
  保留旧 `nv.tar` 传输名；新记录写明压缩格式，恢复明确识别 gzip／旧 plain tar，
  不依赖 BusyBox 自动识别压缩。Android 安装和旧镜像入口的普通 tar 协议保持原样。
- 正常运行阶段按物理内存做离线预估；重启后仍按实际 MemAvailable 检查，
  保留原有 256 MiB 运行余量。已分配的 NV 不再重复计入之后的 RAM 拷贝预算。
- 保留策略的 NV 归档已经包含维护历史，settings 不重复放入 `/etc/e5-nv`；
  无工作 NV 或用户明确选择原机恢复时，settings 继续保留这份历史。
- 错误向安装器返回具体设备末条错误，而不只显示 exit 1。

## 本地验证

新增四项内存／暂存测试，离线更新 21 项、NV 保留 42 项、镜像容量 11 项通过。
包括运行内存低但物理内存充足、实际物理内存不足拒绝、NV 归档不重复计入、
gzip 在 BusyBox 明确解压、配置历史去重及旧恢复格式。
真实只读 OpenWrt chroot 的随机源回退、压缩归档、恢复、校验及异常清理通过。
没有执行用户设备的 NV 同步、原分区写入或自动更新／重启。
